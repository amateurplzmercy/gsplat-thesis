# 测量协议修复与配对复测

第 09 节的总传输、无效预取和淘汰字节保留为流量证据。原来按预算顺序运行的 p99 受环境和运行位置混淆，跨预算延迟排序采用本节复测。

## 环境与对照方法

机器在交流电源下运行。通过系统中已有的 OEM Performance 方案进行测试，执行脚本在结束时恢复原 Silent 方案。PyTorch、OpenMP 和 OpenBLAS 的线程数在本次进程内限制为 1。GPU 时钟随负载变化，使用采样数据核对实际状态。CPU 线程与电源方案一起受控，结果无法单独归因给其中一项。

NVML 和 Windows 计数器约每 0.5 秒采样一次，同时在每遍前后采样。字段包括 SM 和显存时钟、GPU 温度和功率、GPU 利用率、显存使用、CPU 系统与进程负载、进程页错误、进程工作集和交流电源状态。逐帧记录使用同一个单调时钟，便于关联附近样本。功耗采样用于记录运行条件。 [NVML 设备查询](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html)

## 先诊断上传和内存

Playroom 折返、298 MiB，四组都运行 LRU。旧路径使用 pageable CPU 内存和动态拼接。其余三组依次加入预触、64 MiB 固定页环形暂存和预分配 GPU 拼接缓冲。四组以平衡顺序各测四遍。固定页槽在复用前等待对应拷贝完成，拼接缓冲以轨迹峰值工作集分配，块缓存预算单独计数。 [PyTorch 固定页和异步复制说明](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html)

| --- | ---: | ---: | ---: |
| 旧路径 | 18.55 | 5.15 | 0 / 720 |
| 预触 | 19.43 | 6.17 | 0 / 720 |
| 预触 + 固定页暂存 | 20.38 | 7.25 | 0 / 720 |
| 预触 + 固定页 + 复用拼接 | 21.28 | 7.32 | 0 / 720 |

进程每 64 KiB 抽一页，所有组的回放边界抽样页均驻留。旧路径四遍总计 6 次进程页错误，单帧需求阶段最多 1 次。分配器重试和全流同步计数均为零。97 ms 的需求提交尖峰未在受控诊断中复现。页错误计数包含软错误，边界驻留也只反映采样时刻，无法追溯旧日志里尖峰的根因。此次暂存增加 CPU 复制，未观察到尾延迟收益。正式协议统一在计时外预触并核查驻留，沿用原上传与拼接。 [Windows 工作集页信息](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-psapi_working_set_ex_block) · [进程页错误计数](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters)

## 正式复测协议

连续与折返采用 298、326、430 MiB，原始拍摄顺序采用 375 MiB。每档 16 轮，同一档内用四阶 Williams 顺序，每种策略在每个位置出现 4 次。连续和折返在每个策略位置交错三档预算，预算先后位置也轮转。四策略的管线沿用渲染先提交、批量上传和向量化预测。每遍开始清空块缓存，GPU 和分配器先预热，热态分析排除每遍首帧。

同一轮、同一帧相减得到配对帧差，另计算两组分布的 p99 之差。报告中位数、四分位范围、p95 和 p99，以及 2000 次整轮 bootstrap 的 95% 区间。每次重采样为所有策略和预算使用同样的轮次索引，保留连续帧相关性与配对关系。区间对应这些固定轨迹和测试条件。超过 33.3 ms 的样本全部保留，记录最耗时的主机阶段、需求页错误及附近遥测，便于排查原因。

## 原始顺序的上传路径诊断

对 375 MiB 的 LRU 重复同一组诊断，每路径 4 遍。固定页暂存将最大需求提交由预触组的 49.51 ms 降到 36.07 ms，但有需求 miss 的帧上，提交中位数从 4.14 ms 增到 5.17 ms，其中 2.29 ms 用于主机复制。预分配拼接没有改善热态尾延迟。该实现仍使用现有 pageable 需求上传和动态拼接，固定页与预分配路径作为实验开关保留。

## 消融

连续路线使用 326 MiB，每组 16 轮。选择这一格是因为完整管线中的 fixed 在这里有较窄的尾延迟区间，可在相同负载下拆解提交与预测的贡献。

管线实验固定策略和候选块，依次切换渲染先提交、批量上传、向量化。四组每遍均上传 595.69 MiB，其中无效预取 350.50 MiB。批量组额外产生 487.10 MiB 的逻辑 D→D 复制。以下 p99 差均与上一行比较。

| --- | ---: | ---: | ---: |
| 预取先提交，逐块上传，标量预测 | 20.31 | — | 0.00 |
| 渲染先提交 | 16.07 | −4.24［−7.13，−2.87］ | 1.69 |
| 再加入批量上传 | 15.57 | −0.49［−1.59，0.22］ | 4.06 |
| 再加入向量化 | 16.03 | +0.46［−0.48，1.25］ | 4.14 |

批量上传将有预取帧的上传调用次数中位数从 21 降到 1，预取事件窗口从 1.69 增到 4.14 ms。向量化将该组预测耗时中位数从 0.46 降至 0.42 ms。事件窗口包括设备等待和提交间隙，设备复制与内核的实际重叠证据见第 08、09 节 CUPTI 数据。当前消融中，提交顺序的 p99 收益最清晰，批量与向量化的增量区间跨零。

预取策略实验固定优化管线，交叉开关两项设计。缩短并收紧预测把稳定运动的预测跨度由 6 帧降为 2 帧，取预测视锥候选块交集。仅用余量的准入约束禁止预取触发淘汰。两项都开启对应原 guarded。预测跨度和候选交集在此作为一项联合改动。

## short_only 的 Playroom 完整矩阵

连续与折返均用 298、326、430 MiB，原始拍摄顺序用 375 MiB。每格四种策略同轮比较，策略为 LRU、fixed、short_only 和 guarded。每格 16 轮，沿用交错预算、渲染先提交、批量上传、向量化与 16 MiB 预取额度。326 MiB 连续组在同一会话复验。热态统计排除首帧，区间使用 2000 次整轮配对重采样。

流量判据为每遍热态总 H→D 至多高于 LRU 5%。慢帧率判据为 short_only 相对 LRU 的配对差 95% 区间上界低于 +0.5 个百分点。每对帧分别判定是否超过 33.3 ms，再比较两组比例，另报仅 short_only 慢与仅 LRU 慢的帧数。每个区间对应固定轨迹及该次运行条件。

正式计时前，在独立回放中以同块布局的 LRU 为图像参考，逐帧比较 short_only 的浮点 RGB。七格共核对 1041 帧，全部逐像素相同，最大绝对误差均为 0。结果在 `reports/measurement-repair/candidate-matrix/rgb`。

连续三档均同时满足 +5% 流量判据和组 p99 降低。326 MiB 的组 p99 差复测为 −2.75 ms，此前独立对照为 −3.32 ms。298 MiB 的 4.42 MiB 余量对应首帧的峰值工作集，连续路线的热态帧均有至少 16 MiB 的当前必需块之外空间。该空间包含可淘汰的已驻留块。298 MiB 组的每遍需求上传从 LRU 的 250.00 MiB 降为 21.32 MiB，另有 240.80 MiB 预取。尾延迟降低伴随少量总流量增加。

折返 326 MiB 也同时满足两项判据。298 MiB 的组 p99 降低 2.77 ms，总上传比 LRU 多 35.99 MiB，超过 +5% 界线。以折返点第 90 帧为中心取第 85–95 帧，298 MiB 组的需求上传由 17.95 MiB 降至 0.39 MiB，同一窗口新增 21.40 MiB 预取。折返 430 MiB 的组 p99 差区间较宽。折返四策略共出现 14 个慢帧，均出现在 fixed，最长主机阶段均为预取提交。

原始顺序中，short_only 相比 fixed 每遍少传 2122.59 MiB（26.24%），无效预取少 1713.92 MiB（92.93%）。相对 LRU，short_only 的慢帧率为 2.76% 对 2.37%，有 45 对只有 short_only 超阈、31 对只有 LRU 超阈。配对慢帧率差为 +0.39 个百分点，95% 区间为［−0.20，+1.14］个百分点。区间上界高于 +0.5 个百分点，数据支持节省流量，尚不足以确认慢帧率在约定容忍范围内。369 个慢帧中，365 个的最长主机阶段为需求提交。此前三个固定慢帧中，第 15 和 183 帧本轮仍在 64 / 64 遍超阈，第 194 帧为 48 / 64。跳转和需求开销的具体关系留给单独的工作集诊断。
