# 优化管线下的预取策略与预算对照

## 协议与指标

Playroom 的所有策略均使用渲染先提交、批量预取上传和向量化预测的管线。LRU 的预取分支保持关闭。各次回放从空缓存开始，预热与设备追踪和正式计时分离。每个轨迹与预算组合交错测 7 遍，每遍运行四种策略，按平衡轮转顺序切换策略。原始拍摄顺序包含急转和跳转。折返路线把平移路径反向回放，沿用对应位置的相机朝向。

每遍首帧单独计入冷启动。热态 p99、总 H→D 量、无效预取量使用同一批热态帧。总 H→D 量等于按需上传和投机上传之和。无效量包括未使用即被淘汰和回放结束仍未使用的预取字节。总淘汰量包含按需准入与预取准入触发的两部分。设备内拷贝单独统计。

## 批量上传的设备内复制

CUPTI 在拷贝流上分别记录 H→D 和同卡 D→D。枚举值 2 是 D→H，D→D 为 8。同时检查拷贝流有无复制 kernel，以辨别通过 memcpy 或 kernel 实现的设备内复制。连续路线用相同候选、同一缓存预算和向量化预测，分开采集逐块与批量上传。 [CUPTI 枚举说明](https://docs.nvidia.com/cupti/api/group__CUPTI__ACTIVITY__API.html#cupti-activitymemcpykind) · [PyTorch 2.4.1 CUDA copy 实现](https://github.com/pytorch/pytorch/blob/v2.4.1/aten/src/ATen/native/cuda/Copy.cu)

| 上传方式 | H→D 次数 | H→D 设备累计时间 | D→D 次数 | D→D 设备累计时间 |
| --- | ---: | ---: | ---: | ---: |
| 逐块 | 1394 | 58.91 ms | 0 | 0 |
| 批量 | 70 | 49.46 ms | 1394 | 10.05 ms |

两组 H→D 都是 538,828,828 字节，批量组 D→D 字节也为 538,828,828。拷贝流未记录到复制 kernel，全部设备内复制均由 memcpy 实现。D→D 与渲染 kernel 的累计交集为 7.84 ms。70 个有上传帧平均约 0.14 ms 的 D→D 设备时间。独立计时回放的预取窗口均值从 2.91 增至 4.46 ms，帧末等待均值从 0.004 增至 0.075 ms。该窗口还包含 CPU 提交间隙和排队时间，D→D 设备时间只能解释其中一部分。记录位于 `reports/prefetch-study/d2d-single` 和 `reports/prefetch-study/d2d-batch`。

## 主矩阵

每行 p99 为 7 遍热态 p99 的中位数。各流量列为每遍热态字节数的中位数。

| 轨迹 / 预算 | 策略 | p99（ms） | 总 H→D（MiB） | 无效预取（MiB） | 总淘汰（MiB） |
| --- | --- | ---: | ---: | ---: | ---: |
| 连续 / 298 | LRU | 17.82 | 250.00 | 0.00 | 245.89 |
| 连续 / 298 | 固定 | 16.19 | 639.13 | 370.54 | 634.99 |
| 连续 / 298 | 自适应 | 15.57 | 783.08 | 514.48 | 778.87 |
| 连续 / 298 | 保守 | 17.81 | 250.33 | 0.32 | 246.21 |
| 折返 / 298 | LRU | 24.81 | 502.18 | 0.00 | 497.91 |
| 折返 / 298 | 固定 | 50.57 | 1099.76 | 552.61 | 1095.36 |
| 折返 / 298 | 自适应 | 60.42 | 1320.00 | 773.17 | 1315.60 |
| 折返 / 298 | 保守 | 22.84 | 502.78 | 0.61 | 498.51 |
| 原始顺序 / 375 | LRU | 52.27 | 5799.88 | 0.00 | 5601.19 |
| 原始顺序 / 375 | 固定 | 83.19 | 8088.51 | 1844.31 | 7889.88 |
| 原始顺序 / 375 | 自适应 | 78.73 | 6017.68 | 169.08 | 5818.98 |
| 原始顺序 / 375 | 保守 | 53.79 | 5811.24 | 11.35 | 5612.54 |

连续路线的固定和自适应均在 7 轮中低于同轮 LRU。自适应比固定低 5/7，配对 p99 差的中位数为 −0.36 ms。自适应的预测范围在平稳运动时较长，带来更低的按需上传量，同时增加了总上传、无效预取和淘汰。固定方向的无效预取约占投机上传的 72.1%。结合已测重叠，本文可讨论预取流量与尾延迟的取舍。节省的按需等待、已隐藏的传输和额外开销共同影响 p99，当前实验未隔离各自的因果贡献。

原始拍摄顺序上，自适应比固定少 90.8% 无效预取、25.6% 总 H→D 和 26.2% 总淘汰，p99 在 5/7 轮低于固定，在 3/7 轮低于 LRU。保守版的上传与淘汰接近 LRU，三条轨迹相对 LRU 的较低 p99 次数分别为 4/7、5/7、3/7。结果支持把它作为控制带宽开销的策略，尚不足以认定它有稳定尾延迟优势。

折返与原始顺序出现较大墙钟波动。例如折返的 LRU 最慢样本中，需求提交约 97 ms、拼接提交约 44 ms，同一帧选块也达到约 2.5 ms。所有计时样本均保留。字节计数与每轮策略的顺序可复核，较小的延迟差不宜解释为稳定排序。带宽与淘汰压力已直接计量，功耗需独立采样与能耗积分后再讨论实测效果。

## 预算扫描

连续和折返路线在 298 MiB 的基础上增加 326 和 430 MiB。三档对 293.58 MiB 峰值需求的余量约为 4.42、32.42 和 136.42 MiB。每帧真正能用于保守预取的空间还取决于当时已驻留的历史块。原始顺序的峰值超过 326 MiB，沿用 375 MiB 主矩阵。

| 折返 / 430 | 保守 | 53.40 | 314.74 | 0.00 | 178.64 |

更大预算降低了这两条轨迹中所有策略的上传量与淘汰量。以连续路线的保守版为例，298、326、430 MiB 分别提前上传 5.07、31.87、130.91 MiB。326 与 430 MiB 下这些预取块全部被使用，两档总 H→D 与各自的 LRU 完全相同。更多缓存余量确实给保守版创造了提前上传机会。

预算之间依次测量，同一预算内才交错策略。各组尾延迟波动明显，本轮证据支持更大预算减少流量与淘汰，尚不能确定 326 MiB 是 p99 最优点。论文可以把连续 298 MiB 的尾延迟收益和原始顺序的流量收益分别陈述，保留完整对照和波动范围。

## 核对

共完成 196 遍正式回放、29,148 条逐帧计时记录。每个配置内四种策略的逐帧需求与投影数量一致，块预算和流量账本通过检查。连续、折返和原始顺序各抽取 9 帧，四策略的裁剪后浮点 RGB 一致。

## 复现

```powershell
.\run_python.ps1 -m scripts.run_prefetch_matrix --phase main --repeats 7
.\run_python.ps1 -m scripts.run_prefetch_matrix --phase budget --repeats 7
```

输出目录为 `reports/prefetch-study`。每组 `frames.csv` 包含逐帧计时和字节，`summary.json` 保存每轮统计、配对差值及中位数。
